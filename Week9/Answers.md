### Question 1

 `INSERT INTO team ('Avengers', 'Los Angeles')`: Blocked by the `UNIQUE` constraint because the name 'Avengers' already exists.
 `INSERT INTO hero ('Ghost', 99)`: Blocked by the `FOREIGN KEY` constraint because `team_id = 99` does not exist in the `team` table.
 `INSERT INTO hero (age)`: Blocked by the `NOT NULL` constraint because the `name` column cannot be null.
 `DELETE FROM team WHERE id=1`: Blocked by the `FOREIGN KEY` constraint because there is still a row in the `hero` table referencing `team_id = 1`.

### Question 2

Because the Team-Hero relationship is One-to-Many (1 Team has many Heroes, 1 Hero belongs to a maximum of 1 Team). If we place the FK in the `team` table, a cell cannot contain multiple IDs according to the relationship standard; if we place the FK in the `hero` table, each row only needs to store exactly one `team_id` of that hero.

### Question 10

 Remove `session.commit()`: The endpoint returns an object with no valid ID, and the data is not saved to the database at all (SELECT shows empty).
 `add()`: Only marks the object in the current session (staged/unit of work), but does not send data to the database.
 `refresh()`: Reads the record from the database to update the values ​​generated by the database (such as the auto-incrementing `id`) in the Python object.

### Question 13

 The values ​​`18` and `1` appear as replacement parameters (`%s` or `$1, $2`) in a separate parameter block, not directly concatenated into the SQL string.
 This avoids SQL injection because the database compiles the query structure first and then passes the values, preventing the insertion of malicious SQL commands.

### Question 14

1. Performance & RAM: DB filtering only transmits the correct rows over the network to the application, instead of pulling the entire table data, which overloads RAM.
2. Leveraging Indexes: Databases can use B-Tree indexes to filter data at a complexity of $O(\log N)$, while list comprehension in Python requires sequentially traversing the entire database at $O(N)$.

### Question 18

 `upgrade()`: Contains the command `op.add_column('hero', sa.Column('power', ...))` used to add the `power` column to the `hero` table when running to a new version.
 `downgrade()`: Contains the command `op.drop_column('hero', 'power')` used to remove the `power` column from the `hero` table when rolling back to the old version.

### Question 20

 Alembic automatically generates the commands `drop_column('secret_name')` and `add_column('alias')` instead of renaming the column.
 This is dangerous because completely deleting the old column will erase all existing `secret_name` data in the database.
 Solution: Rewrite the migration file content using the function `op.alter_column('hero', 'secret_name', new_column_name='alias')`.
